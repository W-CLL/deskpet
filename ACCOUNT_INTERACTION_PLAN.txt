桌搭子账号与随机互动实施方案
================================

一、确定的产品方向

1. 不做签到、连续天数或每日任务。
2. 桌宠在符合条件时随机发起问候、冷笑话、数学题或趣味题。
3. 激活码是账号入口，不直接作为长期账号主键或登录密码。
4. accountId 是长期数据归属；licenseId + credential 是设备凭据。
5. 互动数据、内容历史和偏好都按 accountId 隔离。
6. 线上内容批量获取并缓存，本地库存不足时后台补充；离线继续使用缓存。

二、账号模型

普通激活码首次使用时创建 accountId 和第一份设备授权。客户端继续使用现有
Bearer licenseId.credential，不需要知道或提交 accountId。服务端完成授权后从
licenses.account_id 得到数据范围，所有账号数据查询都必须使用该范围。

已有授权迁移时，每个旧 licenseId 自动建立一个账号。旧客户端不需要重新输入
激活码，现有 Bearer 凭据继续有效。尚未使用的旧激活码在首次使用时创建账号。

换机使用一次性 rebind 激活码。换机码关联已有 accountId，新设备激活成功后创建
新的 licenseId，并撤销该账号原有设备授权。账号数据不变。第一版保持每个账号仅
有一个有效设备，后续可扩展多设备策略。

三、数据库迁移与部署

所有 SQLite 数据库使用 schema_migrations 表记录已执行版本。Store.initialize()
在服务启动时自动执行未完成迁移；每个迁移在 BEGIN IMMEDIATE 事务中运行，失败
时回滚并阻止服务启动。

同时提供 npm run migrate，供生产重启前手动执行。标准部署步骤：

1. 备份完整 DESKPET_DATA_DIR，包括 db、db-wal、db-shm、密钥和版本文件。
2. 更新代码并执行 npm ci。
3. 可选执行 npm run migrate，提前发现权限、磁盘或数据库问题。
4. 重启单实例服务；未手动执行时，启动过程会自动迁移。
5. 检查 /healthz、管理后台授权数量和客户端更新请求。

不得只复制 activation.db 而遗漏 WAL 或密钥，不得用新的密钥文件替换生产密钥。
数据库迁移只向前执行；回滚应用版本前必须恢复升级前的数据目录备份。

四、随机互动

客户端增加统一 InteractionCoordinator，协调提醒、小剧场、待机台词和互动气泡。
安静、标准、热闹模式分别使用约 90-240、45-120、20-60 分钟随机间隔。心情询问
至少间隔 3-6 小时，同类内容不能连续出现，相同内容至少 30 天内不重复。

互动完成才计数：回答心情、查看笑话答案、回答题目各算一次。气泡只展示后关闭
不计互动次数。开心次数只表示用户明确选择“开心”的次数，不推断真实情绪。

五、线上内容和缓存

内容类型首期为 joke、math、trivia。服务端按账号排除近期已看内容，每批返回
10-20 条；客户端下载不算已看，真正展示后才上报。客户端缓存约 50-100 条，
每类未看内容少于 5 条时后台补充。内容使用稳定 id、revision、catalogVersion、
disabledIds、SHA-256 和 Ed25519 签名，支持停用和完整离线包。

六、互动数据

客户端为每个事件生成 UUID，先持久化到本地队列，累计 10 条或间隔 15 分钟批量
上报。服务端以 eventId 幂等去重，在事务内更新账号汇总。原始事件短期保留，长期
保存互动总数、开心/普通/低落选择、笑话查看、答题和正确次数等账号汇总。

七、实施顺序

阶段 1：版本化迁移、账号表、旧授权迁移、换机码、管理接口和兼容测试。
阶段 2：账号互动档案、幂等事件上报和统计查询。
阶段 3：线上内容库、批量接口、内容管理和离线包。
阶段 4：Windows 随机互动、缓存和同步。
阶段 5：macOS 使用相同契约实现原生交互。

每个阶段必须保持旧客户端兼容并先通过本地自动化测试，再进入生产部署。
